# Reusable Project Management Forms

These forms are repo-native, editable templates for managing the project lifecycle. Replace `{{PLACEHOLDERS}}` with controlled project information and retain completed records in an approved project location.

| Form | When used | Primary control |
|---|---|---|
| [`project-intake.md`](project-intake.md) | Before charter development | Business need, objectives, stakeholders, constraints, and readiness |
| [`charter-approval.md`](charter-approval.md) | Gate 1 | Explicit authorization and conditions |
| [`weekly-status-report.md`](weekly-status-report.md) | Weekly during execution | Health, forecast, accomplishments, risks, changes, and decisions |
| [`raid-entry.md`](raid-entry.md) | When a risk, assumption, issue, or dependency is identified | Ownership, exposure, response, due date, and residual risk |
| [`change-request.md`](change-request.md) | Before changing an approved baseline | Integrated impact analysis and approval |
| [`decision-record.md`](decision-record.md) | For material choices | Context, alternatives, authority, consequences, and review trigger |
| [`meeting-agenda-minutes.md`](meeting-agenda-minutes.md) | Before and after formal meetings | Purpose, decisions, actions, owners, and evidence |
| [`gate-review.md`](gate-review.md) | At phase or authorization gates | Entry criteria, evidence, exceptions, recommendation, and decision |
| [`deliverable-acceptance.md`](deliverable-acceptance.md) | When a deliverable is submitted | Acceptance criteria, defects, evidence, and owner decision |
| [`lessons-learned.md`](lessons-learned.md) | Throughout and at closeout | Actionable learning and follow-up |
| [`project-handoff.md`](project-handoff.md) | Before operational transition | Ownership, access, runbooks, support, training, and open work |
| [`project-closeout.md`](project-closeout.md) | Gate 5 / project end | Objectives, performance, acceptance, transition, archive, and final approval |

## Record-control rules

1. Give each completed record a stable ID and date.
2. Name the owner and approving authority.
3. Link evidence to the exact subject, commit SHA, workflow run, file, or decision.
4. Do not erase rejected options, prior decisions, risks, or conditions.
5. Use approved change control before changing a baseline.
6. Distinguish forecast, assumption, reported result, and verified result.
